# ADR 0002：设置项以注册表为唯一事实源

- **状态**：已接受
- **日期**：2026-09-19

## 背景

每个设置项（见 CONTEXT.md）的生命周期散落在 6 处以上：类型定义、配置默认值、
`setting-utils.ts` 的四件套函数、设置面板组件、`Layout.astro` 里约 300 行手抄的
pre-paint 内联脚本（负责首屏防闪烁 FOUC）、以及 `MainGridLayout.astro` 的 data
属性下发与内联消费。新增一个设置项要人工同步所有位置，且 pre-paint 脚本与
`setting-utils.ts` 是两份需要人工保持一致的实现，没有任何测试保护。

关键约束：pre-paint 初始化必须在首屏绘制**之前**执行（否则主题色相、壁纸模式会
闪烁），因此它不能是打包后的 ES module——module 脚本的加载时机晚于首次绘制。

## 决策

建立一张**设置注册表**作为唯一事实源：每个设置项在注册表里声明存储键、默认值、
应用方式（写入 DOM 的规格）与是否 FOUC 关键。

- 运行期读写经由一个统一的 SettingsStore seam；
- pre-paint 内联脚本在服务端渲染时**由注册表生成**（纯字符串序列化），不再手抄；
- 设置面板的开关/滑杆条目由注册表驱动。

## 后果

- 新增设置项从"改 6+ 个文件"变为"在注册表加一条声明 + 面板一条条目"。
- pre-paint 与运行期逻辑由两份手抄实现变为同一事实源的两种投影，漂移不可能发生。
- 注册表与"状态 → DOM 规格"映射是纯函数，可用 node:test 覆盖（对齐
  `sync-oss-gallery.test.ts` 的既有范式）。
- 存储键保持与历史版本一致，访客已有的本地设置不丢失。
- 界面会持续迭代（见 ADR-0003），注册表本身不包含任何面板 UI，保证改版不伤设置逻辑。
